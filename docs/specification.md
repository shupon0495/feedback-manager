# フィードバックマネージャー 実装仕様書

## 概要

会話や作業中にユーザーから受け取ったフィードバックを保存し、関連する後の会話や作業で再利用するスキルを定義する。

## 実行環境と保存方式

- 実行には `uv` と、`uv` から利用可能な Python を使用する。
- フィードバックは SQLite データベースに保存する。
- SQLite の操作には Python 標準ライブラリの `sqlite3` を使用し、外部 Python パッケージを必須としない。
- 保存先へのアクセスは、同時に操作するエージェントを1体とする前提で扱う。
- スキルは基本的にプロジェクトごとに配置し、別のプロジェクトへ移しても利用できる構成とする。特定の環境の絶対パスに依存せず、パスや設定は移行可能な形で解決する。
- Python は 3.11 以降を対象とする。`uv` のプロジェクト設定に対応バージョンを明記する。
- データベースは基本的に各プロジェクト内の専用ディレクトリに置き、Git 管理から除外する。スキル本体や設定と運用データを分け、スキルの更新時にデータベースを上書きしない。
- 初期版の DB の既定パスは、対象プロジェクトの `.feedback-manager/feedback.sqlite3` とする。`.feedback-manager/` を Git 管理から除外し、SQLite の関連ファイルやエラーログも含める。
- 初期版では DB を配置したプロジェクト内で完結させる。「全般」は当該プロジェクト内の作業全般を指し、プロジェクト間の共有は行わない。プロジェクト間の共有と、それに必要な識別方法は将来の検討事項とする。

## ディレクトリ構成例

以下は対象プロジェクトに配置する場合の例であり、詳細は実装時に調整する。

```text
対象プロジェクト/
├── .agents/skills/feedback-manager/
│   ├── SKILL.md
│   ├── pyproject.toml
│   ├── uv.lock
│   ├── src/feedback_manager/    # 共通の Python 処理
│   ├── adapters/                # ホストごとの連携処理
│   ├── tests/
│   └── docs/specification.md
├── .codex/hooks.json            # Codex のフック設定
├── .opencode/plugins/           # OpenCode のプラグイン設定
├── .feedback-manager/
│   └── feedback.sqlite3         # 運用データ。原則 Git 管理外
└── .gitignore
```

DB とその SQLite 関連ファイルは Git 管理対象から除外する。フックやプラグインは共通処理を参照し、移植先のプロジェクトでもパスを解決できるようにする。

## フィードバックの判断と保存

- モデルはユーザーの発言を文脈に照らして、継続的なフィードバックか、今回限りの指示かを判断する。
- 継続的な希望が明確な場合は保存対象とし、今回限りの指示は今回の作業に適用する。判断できない場合はユーザーに確認する。
- 保存前に既存の関連フィードバックを確認し、新規登録または既存記録の更新を判断する。
- 実際に適用する短い指針に加え、元となったユーザーの文言も記録する。
- Python は指針、元発言、タグなどの入力形式と必須項目を検証し、不正なデータは保存しない。
- Python は識別子や日時の管理、登録、一覧、取得、更新、無効化、削除を行う。
- スキルの配置場所と保存したフィードバックの適用範囲は別に扱う。初期版の範囲は当該プロジェクト内とし、ジャンルごとの対象はタグで区別する。

## 同時アクセスとデータ整合性

SQLite は複数の接続からの同時読み出しに対応する。書き込みは原則として一度に1接続ずつ処理され、読み出しと書き込みの並行性はジャーナルモードなどの設定に依存する。WAL モードは読み出しと書き込みを並行しやすくする。

フィードバック本体とタグなど、関連する複数の変更はトランザクションでまとめ、途中で失敗した場合に一部だけが反映されないようにする。ロックによって書き込めない場合は一定時間待機し、それでも失敗した場合はエラーを通知する。

SQLite が保護するのはデータベースの整合性であり、複数のエージェントが古い内容を基に同じフィードバックを更新することや、指示の意味的な矛盾は別途扱う必要がある。複数エージェントによる更新を将来許可する場合は、更新番号などを使って読み出し後の変更を検出し、上書き前に再確認する方式を検討する。

初期版では上記の単一エージェント前提を維持し、複数エージェントによる同時更新への対応は将来の検討事項とする。

## タグによる取得

- 各フィードバックには複数のタグを付けられる。
- 登録・更新時のタグは自動決定しない。ユーザーに既存タグを提示し、使用するタグ、新設するタグ、またはタグなしを確認する。
- タグの前後の空白を除去し、空のタグと重複を受け付けない。既存タグの一覧を表示し、未登録タグの指定を検出する。
- エージェントは既存タグの一覧を参照し、現在の作業に関連するタグを選択する。
- 取得対象は現在のプロジェクトの DB にある有効な記録に限る。
- 指定したタグのいずれか一つ以上が一致するフィードバックを取得候補とする。
- タグを持たないフィードバックは常に取得候補とする。
- タグは作業内容を表す。初期版では DB がプロジェクト単位の範囲を定める。
- タグによる検索には選択や表記の揺れによる漏れがあり得るため、広く適用する指針はタグなしとするなどして対応する。

## 矛盾への対応

- モデルが適用候補のフィードバック間に矛盾を検出した場合、作業を一時停止し、矛盾点と対象のフィードバックを示してユーザーに判断を求める。
- ユーザーの回答に従って作業を再開する。
- 回答によって継続的な方針が明確になった場合は、対象のフィードバックを更新、無効化、または統合する。
- 今回限りの例外として示された指示は今回の作業に反映し、既存の継続的な指針を自動で書き換えない。継続的な変更か不明な場合は確認する。
- モデルによる矛盾の検出には漏れがあり得るため、ユーザーは保存済みフィードバックの一覧や修正を依頼できる。
- 確認後、モデルはユーザーの回答に基づき更新内容を作成し、Python が対象 ID と入力を検証する。複数の記録を変更する場合は一つのトランザクションで反映する。

## 操作結果とエラー

- Python は各操作の成功・失敗を、状態、エラーコード、説明などを含む構造化された結果として返す。モデルは結果を確認してからユーザーに報告する。
- エラーは日時、操作、エラーコード、説明を記録し、後から確認できるようにする。記録内容や保持期間、保存場所は実装時に決める。
- データベースに書き込めない場合など、エラー自体を記録できない場合も、標準エラー出力などを通じて失敗を通知する。

## 呼び出しと適用

- スキルには、フィードバックを保存・検索するタイミング、取得結果の適用方法、矛盾時の確認手順を明記する。
- 少ないやり取りで、最初の回答や作業からフィードバックを反映できるよう、各ユーザー発言時に検索処理を呼び出すことを目標とする。
- スキルの自動選択だけに依存せず、OpenCode ではプラグインのフック、Codex では `UserPromptSubmit` フックを用いる設定を用意する。各ホストの対応バージョンや設定、フックの信頼状態に依存するため、実際の動作を検証する。
- 両ホストの連携部分は共通の Python 処理を呼び出す。スキル本体、連携設定、データ保存先のパスはプロジェクト間で移行できるようにする。
- 各ユーザー発言時のフックは、現在のプロジェクトの DB からタグなしの指針と既存タグの候補を取得し、モデルに渡す。
- モデルはユーザーの発言と会話の文脈に基づき関連する既存タグを選び、回答や作業に着手する前に、Python を呼び出して該当するタグ付きフィードバックを追加取得する。保存時のタグの登録・変更には別途ユーザーの確認を必要とする。
- 取得結果をモデルに渡す具体的な方法と、呼び出しを利用者に明示する方法は、各ホストの機能を確認したうえで設計する。二段階目のタグ選択と取得はモデルによるツール呼び出しに依存するため、実施や選択の正確さは保証されない。
- フックの実行やフィードバックの取得は、その指針がモデルに正しく適用されること自体を保証しない。取得に失敗した場合は失敗を通知する。

## データと操作の実装方針

- フィードバックには少なくとも ID、指針、元のユーザー発言、有効状態、作成日時、更新日時、および複数のタグを保存する。日時は UTC で記録する。
- Python のインターフェースは、登録、一覧、ID による取得、更新、無効化、削除、タグ一覧、タグによる検索、および複数記録の一括更新を提供する。実装者は CLI の引数と JSON 入出力形式を定義し、利用方法に記載する。
- 登録・更新時のタグは、確認済みの既存タグ、新設するタグ、またはタグなしを明示して渡す。未登録タグの検出と新設操作を区別する。
- 操作結果は成功・失敗と結果データを JSON で返し、失敗時はエラーコードと説明も含める。終了コードでも成否を表す。
- エラーの保持にはプロジェクト内の `.feedback-manager/` 以下のログを使用する。DB を利用できない場合でもログへの記録を試み、ログにも書けない場合は標準エラー出力で通知する。秘密情報や元発言全体をエラーログに含めない。
- 保存されたフィードバックはユーザーの好みとして扱い、現在の明示的な依頼や上位の指示、操作権限を上書きしない。現在の依頼が今回限りの例外である場合は、その依頼を優先する。

## 実装と検証の完了条件

1. 指針と元発言を登録・一覧・取得・更新・無効化・削除できる。
2. タグなしの有効な記録と、指定した既存タグのいずれかに一致する有効な記録を取得できる。無効な記録は適用候補に含めない。
3. タグの登録・変更はユーザーの選択を反映し、未登録タグは意図しない新設をせずに検出する。
4. 複数記録の一括更新に失敗した場合、トランザクションをロールバックする。
5. エラーを構造化して返し、記録を試みる。記録先にも書けない場合は標準エラー出力で通知する。
6. `uv` と Python 標準ライブラリでテストを実行でき、DB や SQLite の関連ファイルが Git 管理から除外される。
7. OpenCode と Codex の対象バージョンで発言時のフック、結果の受け渡し、二段階目の取得を検証する。利用できない環境や未検証の機能は、成功と見なさず前提条件とともに報告する。
8. 固定の環境固有絶対パスに依存せず、別のプロジェクトに配置してパスを解決できる。

