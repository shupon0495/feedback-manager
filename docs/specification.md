# Feedback Manager 実装仕様

## 目的と責務

通常の助言・修正から継続的な好みを読み取り、同じプロジェクトの後続作業に再利用する。保存指示の明示は不要。モデルは意味・継続性・関連タグを判断し、Python CLI は設定、入力、トランザクションを検査する。元発言は実際のユーザー文言を保持し、モデル自身の提案は保存しない。曖昧な希望や一度限りの修正は保存を見送る。

保存内容は好みのデータであり、現在の明示的依頼や上位指示・実行権限を上書きしない。取得や適用の申告だけでは FM の効果を証明できない。

## 設定

プロジェクトルートの `feedback-manager.toml`、または起動側の `FM_CONFIG`（絶対パス）を読み込む。`FM_PROFILE` で選ぶプロファイルはトップレベルの設定を継承する。モデル名やホストからの自動推測はしない。未指定は `ask`、更新可、削除不可。不正設定や未登録プロファイルはエラーとし、緩い設定にフォールバックしない。

| モード | 参照 | 変更 |
| --- | --- | --- |
| off | 禁止。フックにデータを含めない | 禁止 |
| read_only | 許可 | 追加・更新・削除とも禁止 |
| ask | 許可 | 内容を示して承認を受けた変更／batch のみ |
| auto | 許可 | 明確な継続的希望を確認なしで保存 |

`allow_update = false` は更新・無効化・再有効化・取り消しを禁止する。`allow_delete = false` は削除と、記録を除去する取り消しを禁止する。CLI は batch の全子操作にも制限を検査する。確認済みでも禁止操作は許可しない。

承認は書き込みリクエスト最上位の `confirmed: true` で表す。batch の承認は全子操作に適用する。これは呼び出し側の申告であり会話の証明ではない。旧形式のタグ内 confirmed は受理するが、書き込み承認にはならない。

設定ファイル・環境変数を変更できるモデルを OS レベルで隔離する機構ではない。外部設定・環境の固定、コードや DB の直接書き込み制限は起動側の責務。スキルは自己判断による設定変更・制限回避を禁止する。

## 保存とタグ

保存前に既存記録を検索し、重複と矛盾を確認する。タグは既存を優先して自動分類でき、広く適用する好みにはタグを付けない。タグのためだけの追加確認は要求しない。ask では指針・元発言・タグ・変更対象をまとめて確認できる。auto では保存結果を作業の区切りで短く通知する。

矛盾は自動上書きしない。現在の明示的依頼が今回限りの例外ならその作業だけに適用する。解決が必要なら ID と矛盾点を示して確認する。既存変更の禁止を矛盾する新規追加で迂回しない。複数記録の統合は batch で原子的に行う。

検索は有効な記録のうち、指定した既存タグの OR とタグなしの和集合。未知タグはエラー。取得時のタグ選択と意味的な矛盾検出はモデルに依存する。

## 保存方式と履歴

Python 3.11 以降、uv、標準 sqlite3。プロジェクトごとの `.feedback-manager/feedback.sqlite3` を使用する。単一エージェント運用、WAL、外部キー、5秒のロック待機。DB とログは Git 管理から除外する。

スキーマ v2 は元の記録・タグに加えて変更履歴を持つ。書き込み可能なモードで v1 から自動移行し、既存記録を保持する。read_only は既存 DB に読み取り専用接続し、v1 も移行せず参照する。DB 未作成なら空のメモリ DB を使い、プロジェクトに DB は作らない。off は DB に接続しない。

各書き込み／batch は、変更前後の全記録と全タグを履歴へ同一トランザクションで保存する。失敗時には記録・タグ・履歴すべてをロールバックする。履歴には連番 ID、UTC 日時、操作、前後の状態を含める。

undo は最新履歴の ID を要求し、現状態が履歴の変更後状態に一致する場合だけ変更前状態へ戻す。batch は全体を取り消す。取り消しも履歴へ追加する。更新権限を必須とし、記録除去を伴う場合は削除権限も必要。元発言は削除後も履歴に残る。履歴の自動削除は行わず、容量は記録数と変更回数に応じて増える。

## ホスト連携

既存の Codex UserPromptSubmit と OpenCode chat.message 連携を維持する。共通 bootstrap は policy・タグなし指針・既存タグを返し、モデルが関連タグを追加取得する。off なら Codex は空オブジェクト、OpenCode は追加コンテキストもトーストも生成しない。設定エラーや取得失敗を空の成功結果として扱わない。

インストーラーは設定例からプロジェクト設定を初期配置し、既存設定と運用 DB は更新時にも保持する。実行ホストのバージョンと実動検証範囲は verification.md を参照する。

## 入出力と検証

`--view [active|all|history]` は stdin 不要の閲覧コマンドとし、未指定値は active。現在のモード・プロファイル、件数、指針・元発言・タグ・ID・UTC日時を Markdown 表示する。history は変更された記録の前後を表示する。保存テキストは引用し、端末制御文字は文字列化する。DB はモードにかかわらず読み取り専用で開き、未作成でも DB を作らず、旧スキーマも移行しない。off の拒否を維持する。失敗は stderr と終了コード1で知らせる。エージェント経由の閲覧依頼もこの経路を使い、保存や指針適用を行わない。

JSON 入力は1件、最大1 MiB。未知フィールド、重複キー、非 JSON 定数を拒否する。成功は status=ok / exit 0、失敗は status=error / exit 1。CLI の操作と入力例は README.md を正本とする。

元発言や秘密情報をエラーログに保存しない。off/read_only はプロジェクトのエラーログにも書かない。書き込み可能モードのログは1 MiBで1世代ローテーションする。

検証対象は4モード、プロファイル継承・誤設定、全書き込みと batch の権限制限、承認、履歴の原子性と undo、v1 移行、設定の更新時保持、off の両アダプター。モデルによる意味判断や実ホストでの適用は単体テスト成功と区別する。
